# CeyLiving

A marketplace connecting Sri Lankan artisans and entrepreneurs with customers.

Marketplace for independent Sri Lankan makers: the public storefront (build spec T08) plus accounts, seller shops, items, orders, verified reviews, questions and admin moderation (feature spec `CeyLiving_Feature_Spec.docx`, tasks C01–C13). Data lives in PostgreSQL (Prisma 7).

## Run it

Needs Node 22 (`.nvmrc`; `engines` in `package.json`) and Docker Desktop (running).

```bash
npm install
npm run setup
npm run dev
```

Open http://localhost:3000 and pick a demo account on `/signin`. `npm run setup` creates `.env.local`, starts PostgreSQL and Mailpit in Docker, applies the migrations, installs the job queue and loads the demo data (`prisma/seed-data.ts`). `npm run dev` starts the site and the background worker together (see **Background jobs**). Run `npm run db:reset` to start again from the demo data.

## Database

PostgreSQL 17 with Prisma 7 (`prisma/schema.prisma`, migrations in `prisma/migrations/`). Decision record: `docs/adr/0001-schema-grows-per-task.md`.

`npm run setup` does all of this. PostgreSQL listens on `localhost:15432` (so it never clashes with an installed one) and Mailpit's inbox on http://localhost:8025. Both bind to 127.0.0.1 only. After changing `prisma/schema.prisma`, `npm run db:migrate` creates and applies a migration.

- **Two database users (DB-10):** `ceyliving_migrator` owns the schema and runs migrations; `ceyliving_app` (created by `infra/postgres-init/`) can only read and write rows. The first migration grants those rights.
- **Append-only audit log (DB-09):** `ceyliving_app` may not update, delete or truncate `audit_log`.
- **In the schema, not just the code (DB-07):** CHECK constraints for limits and totals, and partial unique indexes for one open application per person (RULE-A1), one open shop per owner and one open report per reporter.
- **Code:** `lib/server/db/tx.ts` holds the handle (`db` and `withTx`, READ COMMITTED, retried up to 3 times on serialization or deadlock errors: DB-05). `lib/server/db/mappers.ts` turns rows into `lib/types.ts` objects (BE-01). ESLint keeps Prisma and the handle's internals inside `lib/server/db/` and `lib/server/repositories/`.
- **Catalogue in SQL (B04b):** filters, sorts and search run in PostgreSQL (`lib/server/repositories/catalogue-search.ts`) and results come in keyset pages: "Load more" fetches the next page from `/api/catalogue/page` and adds it below, and without JavaScript it is a link to the next page. The cursor is opaque and checked; a bad one just gives the first page. Tests compare every filter and sort with the in-memory reference in `lib/catalogue.ts`.
- **Search:** every word must match, as the start of a word, in the item (title, tags, materials, description), its shop's name or its category's English or Sinhala name. Generated `search_vector` columns with GIN indexes back it (migration `catalogue_search`), using the `simple` configuration so English and Sinhala are both indexed. Search text reaches SQL only as letters and digits in a bound parameter (BE-04). When no item matches, suggestions fall back to close spellings with `pg_trgm` ("batk" finds batik).
- **Speed (a benchmark, not a promise):** with 5,814 items on the local Docker database, each catalogue page and search took 12 to 27 ms (median), 37 ms at worst. Real hosting adds network time and will differ with the server and data size.
- **Public pages are cached:** every public read (catalogue pages, search, item, shop and category pages, makers, sitemap) is a small query cached per argument (`lib/server/catalogue.ts`). Each entry is tagged with what it shows, and a change expires only those tags, so the next visit reads fresh rows and every other page stays cached (BE-09, see Performance and caching). Signed-in, seller and admin pages always read the database directly. Because item, shop and category pages are prerendered, `npm run build` needs a reachable, migrated and seeded database (CI starts one).
- **Errors people see:** the services check every rule first, so the database only refuses a write when two requests race. A unique clash (a second open application, a web address just taken, a repeated vote or report) becomes a `ConflictError` with a plain message (`lib/server/db/pg-errors.ts`); any other database error is logged and shown as the generic message with a reference. Raw PostgreSQL text never reaches a page.
- **Seed loader:** `lib/server/db/load-seed.ts` loads the categories and the demo data into every table in one transaction. With `{ replace: true }` it empties the tables first, so running it again never duplicates rows; it refuses to replace data in production.
- **Done so far:** B03a (people: users, applications, addresses, notifications, audit log, rate events) B03b (catalogue: shops, products; content: reviews, questions, answers, reports, helpful votes) and B03c (commerce: orders, seller orders, items, payouts, custom requests). B04a switched the app to PostgreSQL and removed the dev JSON store; its last version is kept in git as the tag `pre-b04a-dev-store`. B04b moved the catalogue, search and paging into SQL.
- **Paid out once (BR-11):** `setPayoutOnSellerOrders` links only orders with no payout yet. If two payout runs race, the second gets a `ConflictError` and rolls back, so no order is ever paid twice. A repository test runs two payouts side by side to prove it. Since B06 the admin button and the weekly job share one service, `runPayouts`, which makes each shop's payout in its own transaction and skips a shop another run has just paid; a test runs both at once.
- **B10 migration (`email_deliveries`):** adds `email_deliveries`, one row per email: a unique `dedupe_key` (template and what it is about), the recipient's user id, the template data and, for account deletion only, the old address, both cleared (a CHECK enforces it) once the email is sent, failed or skipped. Only adds a table. Back up first (`pg_dump`, see the header); the rollback is there too.
- **B08 migration (`payments`):** adds `payments` (unique `provider` + `provider_payment_id`, PAY-04), `refunds` (one live refund per seller order and per whole payment, by partial unique indexes), `orders.paid_at` (required for paid orders; existing ones get `placed_at`), the order payment statuses `REFUNDED` and `PARTIALLY_REFUNDED`, and `shops.payout_hold_reason` / `payout_held_at` (chargebacks). The app can't delete payments or refunds. Back up first (`pg_dump`, see the header); the rollback is there too, and the two new enum values stay unused after it.
- **B07 migration (`checkout_orders`):** adds `orders.payment_status` (PENDING, PAID, EXPIRED), `orders.idempotency_key` (unique per customer), `orders.expires_at`, the seller order status `PENDING_PAYMENT`, `order_items.customization` and `order_items.stock_reserved`, and the `order_number_seq` sequence. Orders that existed before it are marked PAID. The column then has no default, so new code must always set it. Back up first (`pg_dump`, see the header). The rollback is in the header too; the one part that can't be undone is the `PENDING_PAYMENT` enum value, which PostgreSQL can't remove, so it stays unused.
- **B06 migration (`jobs_worker`):** adds `seller_orders.accept_deadline_at` (BR-08; NULL means no deadline, and B08 sets it at payment), indexes for the jobs' lookups, and lets `audit_log.actor_id` be NULL, meaning a scheduled job made the change. The audit pages show "CeyLiving (scheduled job)" and the reason names the job. The migration's header explains the rollback, including the one part that can't be undone once jobs have written audit rows.

## Background jobs

A second process, the worker (`worker/index.ts`, pg-boss 12), runs the jobs of backend plan 10.2 from the same code as the site: the same services, repositories and rules. The queue lives in PostgreSQL (schema `pgboss`), so there is no Redis to run. `lib/server/jobs/queues.ts` lists every job. `worker/handlers/` has one file per job: it checks the payload with zod, calls a service and returns what it did for the log (JOB-01).

| Job                           | When                            | What it does                                                                                                                                                                                                                    |
| ----------------------------- | ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `payouts.generateWeekly`      | Mondays 06:00                   | The payout run (BR-11). The **Generate payouts** button on `/admin/payouts` runs the same service by hand.                                                                                                                      |
| `orders.autoCancelUnaccepted` | Every 15 minutes                | NEW seller orders past their accept deadline are cancelled, and the customer and maker are told (BR-08).                                                                                                                        |
| `orders.autoComplete`         | Hourly                          | Orders dispatched 7 days ago and still not confirmed are marked delivered (BR-17).                                                                                                                                              |
| `customRequests.expire`       | Hourly                          | Open requests and unanswered quotes older than 14 days expire, and the customer is told (FR-14).                                                                                                                                |
| `users.liftExpiredMutes`      | Hourly                          | Mutes that have run out are lifted, the person is told and the change is audited (RULE-M3).                                                                                                                                     |
| `reports.autoHide`            | When a post gets its 3rd report | Hides the post until an admin looks (RULE-M4). Enqueued in the report's transaction, with one queued check per post.                                                                                                            |
| `maintenance.cleanup`         | Daily 03:00                     | Deletes rate events and attempt counters over a day old, expired sessions, expired email links, uploads not finished within a day, deleted accounts' application photos (B09), and finished email records after 180 days (B10). |
| `rateLimits.prune`            | Hourly                          | Deletes sign-in limit rows an hour after their window started (12.4): they hold only IP hashes and stand-ins, but those still link one visitor's requests.                                                                      |
| `orders.expireUnpaid`         | At each order's `expires_at`    | An order still unpaid 30 minutes after checkout is cancelled, its stock comes back and the customer is told (BR-06).                                                                                                            |
| `catalogue.refresh`           | After stock comes back          | Asks the site to drop its cached catalogue: after stock comes back (B07), a shop goes live, or the worker hides a reported review (B13).                                                                                        |
| `payments.reconcile`          | Daily 02:00                     | Compares yesterday's (Colombo) orders with PayHere and reports differences to admins; changes nothing (PAY-08).                                                                                                                 |
| `image.process`               | When an upload is confirmed     | Checks the real file, makes WebP copies at 400/800/1600 without metadata, and marks the upload READY or REJECTED (B09).                                                                                                         |
| `email.send`                  | When a service queues an email  | Sends one email and records the provider's message id (B10). See **Email**.                                                                                                                                                     |
| `email.watch`                 | Every 15 minutes                | Tells the admins about emails that failed or have waited over 30 minutes, each once (B10).                                                                                                                                      |

Times are Sri Lankan time (Asia/Colombo).

- **Created with the change (JOB-02):** `enqueue(tx, name, payload)` (`lib/server/repositories/jobs.ts`) writes the job through the business transaction's own connection, so a job exists only if that change committed.
- **Safe to run twice (JOB-03):** every job selects only rows still in their old state and changes them with a conditional update. A retry, a second worker or a person acting at the same moment never changes a row twice. Each job has a test that runs it twice.
- **Retries (JOB-04):** five tries, about 30 seconds, 1, 2 and 4 minutes apart. A job that fails its last try stays in `pgboss.job` as `failed` and is logged as `job.failed` (level error), and every admin gets a notification. A payload that fails its schema is logged as `job.invalid_payload` and alerted without retrying.
- **Schedules run once (JOB-05):** pg-boss stores schedules in the database and files each tick under one key, so a tick makes one job however many workers run. Scheduled queues also allow only one waiting and one running job.
- **Batches (JOB-06):** jobs that touch many rows take 100 at a time, each batch in its own transaction, until a batch comes back short. A crash loses only the open batch, and the next run carries on.
- **Graceful stop (JOB-07):** on SIGTERM or Ctrl+C the worker takes no new jobs and waits up to 30 seconds for running ones. A job still running then is retried later, which JOB-03 makes safe. A second signal stops at once.
- **Database rights (DB-10):** `npm run jobs:migrate` installs and upgrades the `pgboss` schema as `ceyliving_migrator` and gives `ceyliving_app` row rights only. The site and the worker connect as `ceyliving_app` and never change the queue's structure. A worker that finds the schema missing or out of date refuses to start.

**Running the worker**

- **Development:** `npm run dev` runs both processes, and the worker restarts itself when its code changes. `npm run dev:web` runs the site alone; jobs then wait in the queue and run when a worker starts.
- **Production:** run the site (`npm start`) and the worker (`npm run worker`) as two processes, each kept running and restarted if it stops (in B14 they become two containers from one image). The worker sends every email, sign-in links included, so it must always run. Only the worker gets `EMAIL_DRIVER=resend`, `RESEND_API_KEY` and `EMAIL_FROM`; both need `SITE_URL` (links in emails are built from it). Before starting a new version, run `npx prisma migrate deploy` and then `npm run jobs:migrate`. Stop the worker with SIGTERM (`docker stop` sends it, then waits) and give it at least 30 seconds. Restarting is safe at any time. One worker is enough at launch, and more can run side by side.
- **Watching it:** the worker logs JSON lines with `service: "ceyliving-worker"`: `worker.started`, then `job.completed` (with `job`, `jobId`, `attempt`, `durationMs` and counts), `job.retrying` and `job.failed`. Admins get a notification for every job that fails for good. To look at the queue: `SELECT name, state, count(*) FROM pgboss.job GROUP BY 1, 2;` and `SELECT name, cron, timezone FROM pgboss.schedule;`. Finished and failed jobs stay there for pg-boss's retention period. The admin "Operations" card comes in B12 (OPS-07).
- **Is it running?** `GET /api/health/worker` answers 200 `{"ok":true}` when a worker has checked in within 5 minutes and no email has waited over 30 minutes, and 503 `{"ok":false}` otherwise. Point the uptime monitor at it (OPS-05/OPS-06, set up with the deployment in B13/B14): while the worker is down, nothing inside the app can alert anyone. `/admin/emails` and the admin dashboard say the same in words.

## Logging and request IDs

- **Logger:** `lib/server/observability/logger.ts` (Pino) writes one JSON line per event to stdout: `level`, `time`, `service`, `msg`, `requestId`, plus fields such as `route`, `status`, `durationMs` and `err` (OPS-01). For readable logs in development, run `npm run dev | npx pino-pretty`.
- **Redaction:** passwords, tokens, cookies, authorization headers, account numbers, email, phone and address fields are replaced with `[REDACTED]` up to two levels deep. The key list is `lib/server/observability/redacted-keys.ts`, shared with error reporting (B12). Inside error messages and stacks, email addresses, Sri Lankan phone numbers, `token=`-style values, long digit runs (account numbers) and PostgreSQL's `Key (x)=(value)` are masked (`lib/observability/scrub-text.ts`).
- **Request IDs (OPS-02):** `proxy.ts` runs on every request. It uses Cloudflare's `cf-ray` when it is well formed, otherwise a new UUID, and never trusts a client-sent `x-request-id`. The ID travels upstream in `x-request-id` and comes back on every response.
- **Error wrappers (OPS-03):** `runAction` (server actions) and `withRoute` (route handlers, `lib/server/observability/route.ts`) log each outcome with its duration. Unexpected errors are logged with the stack, and people see a generic message ending in `Reference: <request ID>`. Errors Next.js catches itself go through `onRequestError` in `instrumentation.ts`, which logs the request ID together with the digest that the error page shows as its reference.
- **No console:** ESLint's `no-console` rule applies to `app/`, `lib/`, `components/` and `proxy.ts`. `instrumentation.ts` keeps one `console.error` for a bad environment, because the logger needs a valid environment.

## CI

`.github/workflows/ci.yml` runs on every pull request and on pushes to `main`, `Feature-01` and `Feature-02`: `npm ci` → `npm run check` → `npm run build` → `npm audit` → Gitleaks secret scan. Actions are pinned by commit SHA.

**npm audit:** `npm audit --omit=dev --audit-level=high` blocks CI, so production dependencies must stay clean. The full audit runs too but only reports. It currently shows 5 high findings in dev-only dependencies (`braces` → `micromatch` → `fast-glob` → `eslint-config-next`). They are accepted for now because they run only in ESLint on developer machines and CI, never in the app, and the only offered fix is downgrading `eslint-config-next` to 14, which breaks linting for Next.js 16. Revisit when `eslint-config-next` ships a fixed version.

## Checkout and orders (B07)

The cart stays in the browser. At checkout the browser sends only which items, which variants, how many, the personalisation, the delivery address and an idempotency key made when the page opened. `placeOrder` (`lib/server/services/checkout.ts`) does the rest in one transaction:

- **Who (AU-01):** signed in, with a confirmed email. `/checkout` sends visitors to sign in first. Checkout is limited to 10 a minute per person.
- **Prices from the database (BR-04):** prices, totals and shops are read again; anything else the browser sends is dropped. Items no longer for sale, or from a shop that isn't open, are refused with a message naming them.
- **One order, one seller order per shop (BR-05):** each shop has its own delivery fee (LKR 450, free from LKR 15,000), the same rule the cart shows.
- **Personalisation (BR-16):** checked against the item's own fields (required, length, offered options, nothing extra), then stored as plain text under the field's label at that moment, like the item title.
- **Stock (BR-06):** ready-to-ship items take their quantity from stock with a conditional update (`stock >= quantity`). Of two people buying the last one at the same moment, one gets the order and the other "… just sold out"; asking for more than is left says how many are left. Made-to-order items don't track stock. Variants are always updated in the same order, so carts holding the same items can't deadlock.
- **Waiting for payment:** the order is `PENDING` with `expires_at` 30 minutes ahead, and its seller orders are `PENDING_PAYMENT`. **Sellers see only paid orders**, so a seller never sees an order waiting for payment or one that expired unpaid. The customer's order page shows "Awaiting payment" with the time it is held until and a "Pay now" button. Only PayHere's verified notification moves it on (see Payments).
- **Same key twice (idempotency):** the order row is written first and claims the key, so a double click or a retry gets the same order back and stock is taken once.
- **Expiry:** checkout enqueues `orders.expireUnpaid` for `expires_at` in the same transaction (JOB-02). The job changes an order only while it is still `PENDING` and past its expiry time, so a second run, or a run after the payment arrived, does nothing (JOB-03). A payment confirmed at the same moment waits for the row lock, and exactly one of them wins. The job gives back exactly what checkout took (`stock_reserved`), then enqueues `catalogue.refresh`.
- **Cached stock:** shop pages are cached in the site (see Database). Checkout always reads the database, so a stale page can never sell what isn't there. When stock comes back, `catalogue.refresh` posts to `/api/internal/catalogue-refresh` with `CACHE_REFRESH_SECRET`, and the site expires its catalogue cache. Without the secret (development only) the cache catches up within its lifetime (hours). If the site is down, the job retries.

## Payments (B08, PayHere)

`lib/server/payments/payhere.ts` holds everything PayHere-specific (formulas from PayHere's docs, checked 2026-11-03); `lib/server/services/payments.ts` holds the rules.

- **Paying:** after checkout the customer goes to `/checkout/pay/<order>`. The page builds PayHere's form on the server, with the request hash `UPPER(md5(merchant_id + order_id + amount + currency + UPPER(md5(secret))))`, and sends it once; the button stays for a retry. Card details are entered on PayHere's page only (PAY-01). `order_id` is our order number.
- **Only the notification pays (BR-09, PAY-03):** `POST /api/payments/payhere/notify` reads the form (zod; card fields dropped), checks the merchant ID and `md5sig` (`UPPER(md5(merchant_id + order_id + payhere_amount + payhere_currency + status_code + UPPER(md5(secret))))`, compared in constant time), then that the order exists and the amount (in cents, no floats) and currency equal its total. Anything wrong is logged as a `security.payment_notification` event and answered 200 with nothing changed.
- **Once (PAY-04):** a payment row is unique per PayHere payment ID; a repeated notification finds it and does nothing. Its status only moves forward (pending to success, failed or cancelled; success to chargeback). The order goes `PENDING → PAID` with a conditional update, its seller orders become `NEW` with a 3-day accept deadline (BR-08), and the customer and each maker are notified. `orders.expireUnpaid` makes the opposite conditional update, so when both happen at once exactly one wins (tested in a loop).
- **Status codes (PAY-05):** 2 success, 0 pending, -1 cancelled, -2 failed, -3 chargeback, mapped in one function. A failed or cancelled payment leaves the order held until it expires, so the customer can try again ("Try again" on the result page). A chargeback holds the payouts of that order's shops and alerts admins; an admin releases the hold with a reason (audited).
- **Late money (PAY-06):** a payment for an order that already expired, or was already paid, is recorded and flagged for an admin refund. The order is never re-opened.
- **Result page:** `/checkout/result?order=…` (PayHere's return address) shows the status from the database and re-checks every 2 seconds for 20 seconds while waiting.
- **Refunds (PAY-07, BR-18):** admins only, on `/admin/payments`. Cancelled paid orders and late payments wait in "Needs a refund"; dispatched or delivered orders can be refunded there too (they become `REFUNDED`). A refund is the seller order's full amount (items and delivery), through PayHere's refund API or recorded by hand with the bank reference, and audited. A seller order is refunded once (partial unique index, also when two admins click together). The PayHere call happens between two transactions: a refusal marks the refund failed (it can be retried), and no answer leaves it pending until the admin checks PayHere and records the outcome, because PayHere's refund API has no idempotency key.
- **Who pays for a refund:** the customer gets everything back. If the shop was already paid out for that order, its net share (items + delivery − commission) comes off its next payout (`payouts.refunds_cents`), so CeyLiving bears its own commission. If not, nothing is deducted: cancelled and refunded orders are never paid out.
- **Reconciliation (PAY-08):** `payments.reconcile` looks up yesterday's orders with PayHere's Retrieval API (by order number, at most 20 calls per 10 seconds) and reports to admins: paid here but not at PayHere, paid at PayHere but no notification arrived, amount or status different. It never changes data. It needs `PAYHERE_APP_ID` and `PAYHERE_APP_SECRET`; without them it logs that it skipped.
- **Development:** without `PAYHERE_MERCHANT_SECRET` the pay page says PayHere isn't set up and offers **Simulate payment / failure / cancel**, which sends a correctly signed notification through the same code. The buttons and the action don't work in production. For a real sandbox payment, put the sandbox merchant ID and secret in `.env.local` and point `PAYHERE_NOTIFY_URL` at a public tunnel (for example `cloudflared tunnel --url http://localhost:3000`).

## Photo uploads (B09)

Sellers and applicants upload their own photos. Product, shop and application rows store photo ids, never links (`lib/photos.ts`); seed data and photos saved before B09 keep their Unsplash ids.

1. **Ask (SEC-07):** the photo picker (`components/seller/photo-upload.tsx`) calls `requestUploadAction` with the purpose (item photo, shop logo, shop banner or application photo), the type (JPEG, PNG or WebP) and the size (up to 8 MB). The server checks who may upload what (sellers with an open shop and two-step sign-in; customers with a confirmed email for applications), allows 30 an hour per person, saves a PENDING row under a key it makes (`u/<user>/<uuid>`) and returns an address valid for 5 minutes, signed for that exact type and length.
2. **Send:** the browser PUTs the file straight to storage. The app never receives it, so its 1 MB request limit stays.
3. **Confirm:** `confirmUploadAction` checks that the file arrived at the declared size, then queues `image.process` in the same transaction (JOB-02). Confirming again does nothing.
4. **Process:** the worker (`lib/server/services/image-processing.ts`, sharp) reads the file's real type, checks 300 to 12,000 pixels a side and at most 40 megapixels, makes WebP copies 400, 800 and 1600 wide (never enlarged) with no metadata (no EXIF, no GPS), stores them and marks the upload READY. Anything else is REJECTED with a plain reason. The original is deleted only once the result is stored; a storage error keeps it and the job retries (JOB-04).
5. **Attach (SEC-A2):** saving an item, shop or application keeps the photos it already has. Any other photo must be the person's own READY upload of the right kind; otherwise the field says "This photo isn't available", the same words for someone else's, unfinished or missing uploads (SEC-A5).

**Where files live:** originals and application photos in the private bucket; item and shop photos in the public bucket at `i/<upload id>/<width>.webp`, served from the image domain with a one-year immutable cache. **Application photos are private:** `GET /uploads/private/<id>/<width>.webp` serves them to the applicant and admins only (everyone else gets 404, never cached), and approving an application no longer turns one into the shop logo.

**Development:** with `STORAGE_DRIVER=local`, files go to `.data/uploads/`. `PUT /api/uploads/local` stands in for R2's signed address (an HMAC ticket) and `/dev-uploads/i/…` serves the public copies; both answer 404 with any other driver and in production. Run `npm run dev` (site and worker) so photos get processed. Both processes must use the same folder: `npm run dev` starts them in the project folder; if you start the site from elsewhere (e.g. `next dev ceyliving-f01` from the parent folder), set the same absolute `LOCAL_UPLOADS_DIR` for both.

**Setting up R2 (staging and production):**

- Two buckets, e.g. `ceyliving-uploads` (private, no public access) and `ceyliving-images` (public through a custom domain such as `img.ceyliving.lk`, proxied by Cloudflare). Set the variables above and build with the same `NEXT_PUBLIC_IMAGE_BASE_URL`.
- CORS on the upload bucket, so browsers can PUT to it: allowed origin `SITE_URL`, method `PUT`, header `Content-Type`.
- An R2 API token with Object Read & Write on those two buckets only.
- The CSP (`next.config.ts`) adds the image domain to `img-src` and `https://<account>.r2.cloudflarestorage.com` to `connect-src` at build time.

## Email (B10)

Every email is sent by the worker's `email.send` job, never inside a request (backend plan 11.2). Transactional emails only; no marketing.

| Email                                                | To                      | When                                                                           |
| ---------------------------------------------------- | ----------------------- | ------------------------------------------------------------------------------ |
| Confirm email, reset password                        | the account             | Sign-up or an unconfirmed sign-in; "forgot password" (Better Auth queues them) |
| Seller application decision                          | the applicant           | An admin approves, rejects or asks for changes                                 |
| Order placed                                         | the customer            | PayHere confirms the payment                                                   |
| New paid order                                       | each maker in the order | Same moment: accept within 3 days (BR-08)                                      |
| Order accepted, order dispatched (courier, tracking) | the customer            | The maker moves the order                                                      |
| Delivered, review invitation                         | the customer            | The customer confirms delivery, or 7 days after dispatch (BR-17)               |
| Payout sent                                          | the maker               | An admin marks the payout paid                                                 |
| Post hidden or removed                               | the author              | An admin hides or deletes it, or 3 reports hide it (RULE-M4)                   |
| Account deleted                                      | the old address         | The person deletes their account (FR-17)                                       |

- **Queued with the change (JOB-02):** services call `queueEmail(tx, template, { userId, key, data })` (`lib/server/email/queue.ts`). It adds an `email_deliveries` row and an `email.send` job in the same transaction, so a change that rolls back sends nothing. It never throws: if queueing fails, only the email is undone (a savepoint), the error is logged and the admins are told, and the order, payment or other change still commits.
- **Sent once (JOB-03):** the template and `key` make a unique dedupe key, so an event queued twice sends once. The job sends only a `QUEUED` row and records the result with a conditional update. With Resend, the row id is the `Idempotency-Key`, so a retry after a send that wasn't recorded doesn't send again.
- **Retries (JOB-04):** network errors, timeouts, 429, 5xx and Resend key or domain problems (401/403) are retried on the usual schedule; the last failure alerts the admins. Resend refusing an address or content (400/422) and SMTP 5xx are final (`FAILED`). A deleted account, or an unconfirmed address (except the sign-in emails), is `SKIPPED`.
- **Admins:** `/admin/emails` lists failed and stuck emails with their type, tries, reason in plain words and whether they can be sent again (**Send again**, audited). It never shows addresses or content. Sign-in emails older than an hour can't be resent (their link has expired). The dashboard has an "Emails needing attention" tile and warns when the worker isn't running.
- **Personal data (OPS-01):** job payloads hold only the delivery id. Logs show the delivery id, template, outcome, provider and an error code, never the address, subject or content. The address and data are cleared when an email is final, and the record (template, key, provider id) is deleted after 180 days.
- **Templates:** `lib/server/email/templates.ts`, typed functions with an `html` helper that escapes every value, each with a plain-text version. They are plain functions, not React: the worker runs with React's server-components build, where `react-dom/server` can't be loaded.
- **Development:** `npm run dev` runs the worker; open http://localhost:8025 (Mailpit) to read every email. Without the worker, emails wait in the queue.
- **Production (Resend):** before launch, verify the sending domain in Resend with SPF, DKIM and DMARC (11.2), create a send-only API key limited to that domain, and give it to the worker only. Bounces and complaints (Resend webhooks) aren't handled yet.

## Bank details (B11)

Sellers' account numbers are encrypted with AES-256-GCM before they're stored (`lib/server/crypto/field-encryption.ts`), and a database check refuses anything that isn't encrypted. Bank, branch, holder name and last four digits stay readable, so the pages never need the key.

- **Who sees what:** sellers see the last four digits of their own account, and can replace it but never read it back. Admins see the bank and last four in the payouts list. The full number needs **Show bank details** on one scheduled payout that isn't on hold, plus the admin's password every time. The worker can't reach it (a test walks its imports).
- **Audit:** a reveal writes `payout_account.revealed` in the same transaction as the read, and nothing is shown unless it commits. Failed attempts write `payout_account.reveal_failed` with a reason code. Five failed attempts (wrong password or refused role) lock the reveal for 15 minutes, and an admin can make 60 reveals an hour. Saving or replacing details writes `payout_account.saved`, and a replacement also notifies and emails the seller.
- **An admin needs a password.** An account with none (for example a demo account) is told to set one with "Forgot password".
- **Wrong key:** the reveal is refused, the failure is audited, and nothing is shown. Masked details, statements and marking paid keep working, because they don't decrypt. `npm run payouts:reencrypt -- --check` finds rows that can't be read.
- **Keep the key safe.** Store it in the server's secret store, never with the database or its backups, and keep a secure offline copy. Without it, stored numbers can't be read and sellers have to enter them again.
- **Account deletion and export (FR-17):** export shows the last four digits only. Deletion removes the details of the person's closed shops, and waits while a payout is still owed.

**Rotating the key** (planned, or at once after a suspected leak):

1. Run `openssl rand -base64 32`. Set the result as `FIELD_ENCRYPTION_KEY`, move the old key to `FIELD_ENCRYPTION_PREVIOUS_KEYS`, and restart the site.
2. Run `npm run payouts:reencrypt`. It prints counts only, can be stopped and run again, and exits with an error if any row couldn't be read (that row is left alone).
3. Run `npm run payouts:reencrypt -- --check`, confirm that only the new key is listed, remove the old key from `FIELD_ENCRYPTION_PREVIOUS_KEYS`, and restart.
4. Keep the retired key offline for 30 days: a restored nightly dump (backend plan 17.4) needs the key it was made with. After a leak, dumps made before the rotation stay readable with the leaked key until they age out, so count them in the breach assessment.

## Monitoring and request protection (B12)

- **Health checks (OPS-05):** `GET /api/health` answers 200 while the process runs, without touching the database (for a container health check). `GET /api/ready` answers 200 when the database answers within 2 seconds and this build's newest migration (`lib/server/db/expected-migration.ts`) is applied; otherwise 503. Both say only `{ "ok": … }`; the reason is in the log line `ready.failed`. An uptime monitor should call `/api/ready` and `/api/health/worker` (B10). A database ahead of the build (a newer migration already run) still counts as ready. **Add a migration, update `EXPECTED_MIGRATION`**: a test fails until you do.
- **Request protection (12.2):** every route handler goes through `withRoute`. POST, PUT, PATCH and DELETE need an `Origin` equal to `SITE_URL`'s (outside production, the request's own host too), else 403, and a body of at most 1 MB, else 413 (the bytes are counted, so a false `Content-Length` doesn't help). Exceptions are written in the route: PayHere's notification (signed, 64 KB) and the worker's catalogue refresh (secret) need no `Origin`; the dev upload route enforces its own size. A test fails if a mutating route skips `withRoute`. Server Actions keep Next's same-host check and 1 MB limit (`next.config.ts`).
- **IP addresses (12.4):** never stored as the address.
  - **Our own data:** a keyed hash (HMAC with `IP_HASH_KEY`, 32 hex characters) in our sign-in limit keys and in `audit_log.ip_hash`. Sessions don't keep the IP.
  - **Better Auth's limiter:** Better Auth keys its own limit rows `<ip>|<path>` and has no option to hash them. So `/api/auth` (`withRateLimitPseudonym` in `lib/server/security/ip.ts`) removes every proxy IP header, including any copy of ours a client sent, and sets `x-ceyliving-rl-ip` to a stand-in: `fd` and 56 bits of an HMAC of the IP under `IP_HASH_KEY`, as an IPv6 address. It is the only header Better Auth reads (`advanced.ipAddress.ipAddressHeaders`). Better Auth's counting, windows and storage are unchanged; only the address it counts by is different. The visitor's IP is found by Better Auth's own rules: `cf-connecting-ip`, else `x-forwarded-for` when it names one address, normalised (IPv6 by /64).
  - **Proxy trust:** both headers are only as good as the proxy that sets them. Production must be reachable only through Cloudflare (or a proxy that overwrites these headers), never directly, or a visitor could pick a new IP, and so a new limit, per request.
  - **Retention:** the hashes and stand-ins still link one visitor's requests, so they are pseudonymous personal data, not anonymous. `rateLimits.prune` deletes every `rate_limits` row an hour after its window started. Migration `20261110130000_rate_limits_purge_raw_ips` deleted the raw-IP rows written before this.
  - **Rotating `IP_HASH_KEY`:** every sign-in limit starts over (a burst of attempts right after the change isn't counted against the old ones), and audit rows written before and after can't be linked by `ip_hash`. Nothing else changes, and nothing needs re-hashing. Rotate it when it may have leaked, and not on a schedule.
- **Audit rows (OPS-02):** every audit row written during a request carries its `request_id` and `ip_hash`, so a row links to its log lines. Rows from the worker, and rows written before B12, leave both empty.
- **Security events (A09):** `ops_event_counts` holds counts per kind per 5 minutes, and nothing else (no person, IP or id), for 30 days. Counted: failed sign-ins and wrong two-step codes, sign-in limits reached, refused actions (no permission), payment notifications with a bad signature, failed, locked and successful bank-detail reveals, server errors, failed jobs, refused Origins and oversized requests.
- **Alerts (OPS-06):** the worker's `ops.watch` job runs every 5 minutes and checks the rules in `lib/config.ts` (`OPS_ALERT_RULES`, `OPS_LIMIT_RULES`). **Critical** (an email and an in-app notification to every admin): server error spikes, failed jobs, bad payment signatures, many failed sign-ins, unusual bank-detail reveals, database connections or size, disk, and backups (silent until B14 records a first backup). **Normal** (in the app only): sign-in limits, refused actions, refused Origins and oversized requests. Each kind alerts at most once an hour while it continues, and once sooner if it gets 4 times worse ("Getting worse"). A new queue needs `npm run jobs:migrate` before the worker starts, as every deploy does.
- **Operations card (OPS-07):** on `/admin`, below the tiles: the worker, failed jobs (7 days), queues, the last payout run, the last backup, emails, the last 24 hours' security events, and the last alert (with failed alert emails).

## Performance and caching (B13)

Measured on a production build with 1,000 items, 4,900 reviews and 10 shops (`scripts/load/grow-catalogue.sql`). The database is not the limit: every catalogue query has a p95 of 35 ms or less. The cost is rendering, 40 to 110 ms of CPU a page even when every read is cached, and one Node process renders one page at a time. With k6 on a warm cache, one process passed at 7 requests a second (p95: catalogue 96 ms, items 139 ms, shops 91 ms). At 10 a second it is at its limit: catalogue and shop pages pass, but item pages measured 171 to 314 ms across runs. More traffic needs more web processes (B14), not more caching.

**A whole-catalogue refresh is expensive.** Afterwards every page renders again on its next visit, about 400 ms of CPU each, so 1,000 item pages cost minutes of CPU. Under load, that pushes responses to seconds until the pages are warm again. This is why changes refresh only their own tags, and why `catalogue` is kept for rare events. Run load tests on a warm cache (see "Load test" below).

**Targeted refresh (BE-09).** Every cached read carries `catalogue` plus tags for what it shows (`lib/server/catalogue-tag.ts`). A change expires only these:

| Change                                                                                | Tags expired                                                                       |
| ------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| Item saved, archived, restored, or decided by an admin                                | `product:{id}`, `shop:{slug}`, `category:{slug}`, `products` (site-wide lists)     |
| Order placed                                                                          | `product:{id}` of each item it took stock from                                     |
| Review posted, edited, replied to or moderated                                        | `reviews:{productId}`, `product:{productId}`, `shop-reviews:{shopId}`              |
| Shop edited, suspended or reinstated; an account deleted (anonymised names)           | `catalogue` (everything)                                                           |
| Questions, answers, helpful votes, reports, notifications, payouts, custom requests   | none: they are read fresh on every visit; the person's page re-renders (`refresh`) |
| Worker changes (stock back, a shop going live, a reported review hidden at 3 reports) | `catalogue`, through the `catalogue.refresh` job, within seconds                   |

Every list also carries the tag of each item it shows, so a list refreshes when one of its items changes or leaves (a moved category included). `revalidatePath("/", "layout")` is no longer used anywhere. A list's _order_ by rating can trail a new review until that list refreshes or the cache's hour runs out; the numbers on the item itself update at once.

**Bounded reads.** The shop page shows 12 items and "Load more" (`/api/catalogue/page?shop=…`; without JavaScript, `?after=`), and its 6 latest reviews come from one query with `LIMIT 6`. Q&A answers, `/makers` counts and ratings, category tile counts and the `/admin/sellers` table each use one grouped query instead of one per row.

**Manual check (done for B13):** this was run on `next dev` against the 1,000-item database, because production refuses demo sign-in, with PostgreSQL logging every statement. The demo seller changed one price on item A (`naga-raksha-mask`). Afterwards, item B (`batik-paisley-shirt`), its category and its shop ran no catalogue queries: they were served from the cache. Item A ran 3 and showed the new price at once, and A's category, A's shop and `/search` ran 1 each. A second visit to A ran none.

**Load test (k6).** Against a production build (`next build && next start`) on a copy of the data:

1. Create a database whose name ends in `_perf`, then run `npx prisma migrate deploy`, `npm run jobs:migrate` and `npm run db:seed` against it, with `DATABASE_MIGRATION_URL` pointing at it.
2. Grow it to 1,000 items: `npx prisma db execute --file scripts/load/grow-catalogue.sql`, same URL. The script refuses any other database.
3. Build and start the site with `DATABASE_URL` pointing at that database.
4. Run `BASE_URL=http://host.docker.internal:3000 npm run load:k6`. This uses the pinned `grafana/k6` Docker image. `RATE` sets requests a second (default 10) and `DURATION` sets the run length (default `2m`). `SESSION_COOKIE`, a signed-in session cookie copied from the browser, adds the checkout page and the cart lookup. The run places no orders.

The run fails if the p95 of catalogue, item, shop or checkout requests passes 300 ms, or if more than 1% of requests fail. Start on a warm cache: visit every address in `/sitemap.xml` once (twice is safer) after the server starts and after any whole-catalogue refresh. Otherwise the test measures the first renders, not the site.

## How the code is organised

Requests follow the feature spec (section 7.2): **form → server action → service → repository → PostgreSQL**.

- `lib/server/actions/*` — thin server actions: who is asking (`requireActor`) → validate with zod (`lib/validation/*`) → call a service → revalidate → return `{ ok, message, fieldErrors }`.
- `lib/server/services/*` — every business rule (RULE-A, S, P, R, Q, M, N), status-flow tables and audit rows. Async functions of an actor and input that open their own transaction with `withTx` (BE-02), so they are unit-tested directly.
- `lib/server/repositories/*` — the only code that reads or writes stored rows (BE-01). Every function is async and takes a handle first: `findUserById(db, id)` for a read, `updateSellerOrder(tx, id, patch, { from })` inside a transaction. Status changes are conditional updates: they return nothing if the status changed first (DB-06).
- `lib/server/db/tx.ts` — the handle: `withTx(fn)` runs one all-or-nothing transaction (DB-04); `db` is the shared read-only handle for pages (BE-03).
- `lib/server/permissions.ts` / `auth.ts` — `requireUser`, `requireRole`, `assertShopOwner`, `canPost`.

**From the dev store to PostgreSQL (backend plan 6.2):** B02 moved all data access behind async repositories and `withTx`, B03 built PostgreSQL versions of them, and B04a switched over and deleted the dev JSON store. Services, actions and pages did not change.

## Security

- **Sign-in (B05a, Better Auth):** email and password, with the email confirmed before posting, selling or checking out (AU-01). Passwords need 10+ characters and are checked against known data breaches; Better Auth hashes them. Messages never reveal whether an email has an account (AU-07). Sessions live in PostgreSQL behind an HttpOnly, SameSite=Lax cookie (Secure in production), last 7 days idle and 30 days in all, and end on a password change or reset, a role change and account deletion; "Sign out everywhere" is on `/account` (AU-03, AU-04, AU-11). Sign-in, sign-up and reset allow 5 attempts per 15 minutes per email and per IP, counted in the database so every app instance shares them (AU-06). Emails go out over SMTP (Mailpit locally). `getSession()` returns the same `{ user }` as before (AU-05).
- **Two-step sign-in (B05b):** an authenticator app (TOTP, set up with a QR code or a typed key) or a passkey. Sellers and admins need a session opened with two steps before `/seller` or `/admin` opens; without one they go to `/account/two-step` and back (AU-02). Seller and admin actions check the same thing on the server, so calling them directly is refused too. A passkey must be unlocked with the device's PIN or biometric, so it counts as two steps alone. Ten recovery codes are shown once and stored only as keyed hashes (HMAC with `BETTER_AUTH_SECRET`); each works once. There is no "trust this device". Once an account has a second step, adding or removing one needs a session opened with two steps, so a stolen password can't add an attacker's passkey. Sellers and admins can't turn the app off. Turning two-step on (confirming the app, or adding a passkey) gives this browser a fresh session and ends every other one (AU-04).
- **Passkeys:** anyone can add one under "Sign-in and security" on `/account` and sign in with it on `/signin` (`@better-auth/passkey`, WebAuthn; only the public key is stored).
- **Turnstile (AU-06):** always on sign-up and password reset, and on sign-in after 3 failed attempts for that email or IP in 15 minutes. The token is checked with Cloudflare on the server (`lib/server/turnstile.ts`); if Cloudflare can't be reached, the check fails. Better Auth's own `/api/auth/sign-in/email`, `/sign-up/email` and `/request-password-reset` routes, called directly, always need a token.
- **Admin sessions (AU-03):** end 12 hours after sign-in, or after 2 hours without use (use is recorded at most every 15 minutes, so up to 15 minutes later).
- **Server checks:** every protected layout, page and action checks the session and role on the server (SEC-A1). Hidden buttons are never the check. `proxy.ts` is only a fast first redirect for visitors with no session.
- **Ownership:** sellers' shops are always loaded by owner, never from IDs in the form (SEC-A2). Other people's orders, items and shops return 404 (SEC-A5).
- **Input:** all input is validated with zod (SEC-A3). User text is rendered as plain text (SEC-A4). Questions, answers, reviews and replies can't contain emails, phone numbers or links (RULE-Q4).
- **Rate limits:** posting actions are rate-limited per user (SEC-A6; limits in `lib/config.ts`).
- **Admin actions:** every admin action needs a confirmation, a reason where the rules require one, and writes an append-only audit row in the same transaction (SEC-A9).
- **Server-only code:** server modules start with `import "server-only"` (SEC-A7). Demo sign-in is impossible in production, and tests prove it (SEC-A8).
- **Buyer details:** sellers see a buyer's name, address and phone only for their own orders, and only until 30 days after delivery (SEC-A10).
- **Response headers:** Content-Security-Policy, HSTS (production), X-Frame-Options, X-Content-Type-Options, Referrer-Policy and Permissions-Policy are set in `next.config.ts`.
  - The CSP allows `'unsafe-inline'` scripts because nonces are incompatible with Partial Prerendering.
  - Images come from this site, the image domain (B09) and the Unsplash CDN (seed photos); uploads go only to the R2 upload endpoint (`connect-src`).
- **Uploads (SEC-07, B09):** signed 5-minute upload addresses for JPEG, PNG or WebP up to 8 MB; the worker checks the real file and re-encodes it, which strips EXIF and GPS; originals and application photos stay private.
- **Request protection, IPs and alerts (B12):** see "Monitoring and request protection".
- **Errors:** unexpected errors are logged on the server and shown to people as a generic message with a reference ID (CS-14, OPS-02).

**Also included:**

- **Helpful votes:** reviews and questions can be voted helpful, and are sorted most helpful first (FR-19).
- **Payouts:** the weekly payout job (BR-11) runs in the worker on Mondays, and the button on `/admin/payouts` still runs it by hand.
- **Account deletion:** deleting an account anonymises it and keeps order records (FR-17).

**Not production-ready yet:** email through a provider (B10) and the remaining backend tasks are still required before launch.

## Tests

`npm test` runs every test against PostgreSQL. Docker must be running: a Vitest global setup (`test/global-setup.ts`) starts one throwaway PostgreSQL with Testcontainers, applies the real migrations and installs the job queue, each test file gets its own copy of that database, and the demo data is loaded again before every test (`test/db.ts`). Without Docker the run stops with a clear message instead of skipping database tests.

- **Unit tests:** every business rule, named with its ID (for example `RULE-R1 blocks a review without a delivered order`).
- **Permission tests:** every server action is called as a guest, plus wrong-role and other-owner cases.
- **Sign-in (`lib/server/auth-flows.test.ts`):** sign up, confirm by email, sign in; same answers for unknown emails; breached passwords refused; one-time reset links; sessions ended on reset, password change, role change and deletion; the 30-day limit; attempt limits shared across instances; a customer with a real session calling admin and seller actions directly is refused and nothing changes.
- **Two-step, passkeys, Turnstile (`lib/server/two-step.test.ts`):** sellers and admins without two-step are sent to set it up and their actions are refused; TOTP set-up and sign-in; other sessions ended on set-up; recovery codes stored hashed and single-use; Turnstile refused without a valid token, checked on the server (Cloudflare stubbed, never called); admin session limits.
- **Production guards:** demo sign-in is impossible in production, and an old or forged demo cookie signs no one in.
- **Repositories (`test/repositories/`):** each repository against PostgreSQL, plus what only the database enforces: DB-05 retries, DB-07 constraints, DB-09 and DB-10 rights, one payout per order, and a seed loader that can run twice.
- **Caching:** each change expires only the tags of what it shows; questions, votes and reports expire none; failed changes expire nothing (BE-09).
- **Transactions:** a failed step writes nothing (DB-04), a status that changed first gives a clear conflict (DB-06), and the shared read handle refuses writes (BE-03).
- **Environment:** `lib/env.ts` refuses demo login in production (AU-09), requires real Turnstile keys there (AU-06) and names bad keys without echoing values.
- **Logging (OPS-01 to OPS-03):** redaction of secrets and personal data, request-ID rules, the proxy's header and redirects, and the `runAction` and `withRoute` references.
- **Header components:** the header's sign-in states and menus.
- **Background jobs (`worker/jobs.test.ts`, `worker/worker.test.ts`):** every job run twice (JOB-03) with its rule (BR-08, BR-11, BR-17, FR-14, RULE-M3, RULE-M4); the admin payout button and the weekly job at the same moment pay each order once; 250 rows handled in batches of 100 (JOB-06); a job enqueued in a rolled-back transaction never exists (JOB-02). With real pg-boss workers: two workers run one schedule tick once (JOB-05), a failing job is retried and then alerts the admins (JOB-04), and stopping waits for a running job, up to its time limit (JOB-07).
- **Uploads (`lib/server/services/uploads.test.ts`, `lib/image-loader.test.ts`):** a non-image or oversized file is rejected; processed images have no EXIF or GPS; WebP sizes are made without enlarging; application photos never reach the public bucket and only the applicant and admins can open them; a seller can't attach another user's upload (SEC-A2); confirming and processing are safe to repeat (JOB-02, JOB-03); a storage error keeps the original (JOB-04); unfinished uploads are cleaned up; the migration keeps every application's photos.
- **Full journey:** apply → approve → set up → post → approve item → buy → deliver → review → ask → answer → report → hide.
